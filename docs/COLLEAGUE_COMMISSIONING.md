# Наладка прибора и запуск процедур из таблицы

Этот маршрут рассчитан на инженера, у которого есть прибор и возможность проверить
трубки, датчики и движения. После прохождения остаются профиль прибора с измерениями,
настроенные процедуры и один экспортируемый комплект для передачи коллеге.

Начните с меню **Наладка** (`/commissioning`). Таблицы оборудования находятся в
**Config**, процедуры — в **Procedures**, ненайденные механизмы двигаются через
**Valve bench** / сервисное движение на странице **Control**.

## 1. Установка и запуск

Из корня репозитория, Python 3.11 или новее:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
pytest
FLOWENGINE_CONFIG_DIR=./local-config-mock python -m flowengine --mock
```

В Windows активируйте `.venv\Scripts\Activate.ps1`, затем:

```powershell
$env:FLOWENGINE_CONFIG_DIR="./local-config-mock"
python -m flowengine --mock
```

Откройте `http://127.0.0.1:8765/`. Mock нужен для проверки установки и интерфейса;
его результаты нельзя выдавать за физические калибровки.
Остановите mock (`Ctrl+C`; закройте вкладки при долгом завершении).
Для прибора используйте отдельный каталог:

```bash
FLOWENGINE_CONFIG_DIR=./local-config python -m flowengine --serial-port /dev/cu.usbmodemXXXX --serial-baud 115200
```

Windows: `$env:FLOWENGINE_CONFIG_DIR="./local-config"`, затем
`python -m flowengine --serial-port COM3 --serial-baud 115200`.
Номер COM или путь macOS возьмите у фактически подключённой платы.
Ошибка `address already in use` означает, что другой сервер уже занимает 8765:
сначала остановите его, не запускайте два процесса на один USB-порт.

## 2. Где и когда сохраняются данные

На странице **Наладка** показан абсолютный каталог конфигов именно этого запуска.
При командах выше это `local-config` в каталоге проекта.

| Данные | Место | Когда записываются |
| --- | --- | --- |
| Оси, пределы, насосы, рабочие положения, маршруты, runtime | `profiles/bench_instrument.yaml` | «Сохранить JSON профиля» либо Save current as… в Config |
| Сырые измерения насоса и рассчитанный коэффициент | Тот же профиль, `commissioning[]`; коэффициент также в `device_map.pumps[]` | «Рассчитать и сохранить измерения и коэффициент» |
| Рабочие координаты крана и описание трубок | Тот же профиль, `device_map.valves[]` и запись в `commissioning[]` | «Сохранить калибровку крана в профиль» |
| Успешные и неуспешные запуски процедур, результаты HOME, последние TX/RX | Тот же профиль, записи `kind: procedure_run` | Автоматически, если активирован именованный профиль |
| Результат физического наблюдения, измеренные объёмы контрольных доз, допуск | Тот же профиль, `commissioning[]` | Вручную в блоке «Журнал проверок» сразу после опыта |
| Ручная установка нуля и наладочные jog со страницы Наладка | Тот же профиль, `reference_result` / `motion_result` | После действия со страницы Наладка |
| Измерение периода U | Тот же профиль, `period_result` | После успешного измерения со страницы Наладка |
| Шаги процедур, направления HOME, объёмы, расходы, число циклов по умолчанию | `procedures/ИМЯ.yaml` | Save / «Save run parameters as defaults» в Procedures |
| Переносимый комплект | Скачанный `bench_instrument-handoff.json` | «Скачать профиль, журнал и процедуры» |

**Save & preview не сохраняет введённые параметры запуска как defaults.**
Для их постоянного сохранения нажмите **Save run parameters as defaults**.
Иначе после повторного открытия процедуры вы снова увидите старые defaults.
Локальный файл `procedures/ИМЯ.yaml` перекрывает одноимённый файл репозитория.

Кнопки сохранения калибровок изменяют **сохранённый профиль**, не живое оборудование.
После завершения нужной группы изменений нажмите **Применить сохранённый профиль**.
Это не перемещает моторы и не переоткрывает USB, но сбрасывает все `homed`:
нужно заново найти или физически установить нули. Изменение порта, baudrate или
firmware требует перезапуска с `--profile bench_instrument`.

Текущие координаты и `homed` намеренно не восстанавливаются из файла после
отключения моторов, изменения профиля и перезапуска. Журнал содержит историю,
а не разрешение верить старому физическому положению.

## 3. Подготовить свой профиль

1. Откройте **Наладка**, нажмите **Взять активные настройки**.
2. Задайте имя `bench_instrument`, нажмите **Сохранить JSON профиля**.
3. Откройте JSON или таблицы **Config**. В Config выберите свой сохранённый профиль
   и нажмите **View selected**, прежде чем редактировать.
4. Сначала сверяйте карту, затем сохраните изменения. Для отредактированного JSON
   в Config сначала нажмите **Load forms from JSON**, иначе старые формы могут
   конфликтовать с JSON. Можно редактировать JSON непосредственно в Наладке.
5. Для движения установите `runtime.motion.enabled: true` после проверки карты;
   оставьте `runtime.motion.configure_firmware: false`.
6. Примените профиль через **Наладка**. В `/api/state` должно быть
   `profile: bench_instrument`, `connected_idle`, `motion_enabled: true`.

В дальнейшем запускать сразу с профилем:

```bash
FLOWENGINE_CONFIG_DIR=./local-config python -m flowengine --profile bench_instrument
```

Перед физическим опытом держите доступным отключение питания приводов.
В нашей прошивке `EMERGENCY_PARSER` отсутствует: экранный ABORT не заменяет
физический выключатель. После потери связи состояние координат непроверено.

## 4. Карта, датчики и единицы

Подтверждённая ранее карта этой установки; коллега сверяет её с текущей сборкой:

| Ось | Разъём Monster8 | Устройство |
| --- | --- | --- |
| X | DRIVER0 | Шприц пробы |
| Y | DRIVER1 | Шприц обжимающей жидкости |
| A | DRIVER3 / E0 | Кран промывки |
| B | DRIVER4 / E1 | Кран обжимающей жидкости |
| C | DRIVER5 / E2 | Кран пробы |
| U | DRIVER6 / E3 | Перистальтический насос промывки |

У каждого крана ровно один концевик. Три концевика A/B/C подключены параллельно
к `z_min`, поэтому HOME выполняется последовательно. Для всех трёх на стенде
подтверждено направление **−1**. В `home_valves_shared` defaults направлений уже −1.

Для X/Y/U не предполагаем заранее ни исправность, ни неисправность датчика.
Проверьте каждый физически и кнопкой **Read endstops** установите имя входа.
Для Y раньше сообщалось о неисправности; это историческое наблюдение, не диагноз
текущей сборки. Для U состояние и подключение датчика ещё предстоит выяснить.
Запишите входы и подключённые оси в `device_map.endstop_inputs`, наблюдения — в журнал.
Запись `endstop_inputs` сама не переназначает входы G28 в прошивке.

Через **Read settings / M503** сверьте `M92` и `M203`. В профиле:

- `axes[].steps_per_unit` должен совпадать с реальным `M92`;
- `feedrate_max` задаётся в единицах/мин, `M203` — в единицах/с: умножаем на 60;
- `home_direction: min` означает допустимые координаты `[0, travel]`;
- `home_direction: max` означает `[-travel, 0]`;
- `travel` — измеренный допустимый ход от нуля, не дистанция HOME и не объём шприца.

У кранов «единица оси» пока не является измеренным миллиметром или градусом вала.
Не переводите единицы и M92 без реального измерения. Числа хода в исходном профиле
взяты из прототипа и остаются предварительными. В частности, у C успешный отход
уже дал координату около 11 при прежнем шаблонном `travel = 10.1065`.
Перед обычным позиционированием требуется измерить и исправить этот предел;
не обходить ошибку границ выставлением произвольного огромного числа.

## 5. Повторяемость HOME кранов

Откройте **Procedures → home_valves_shared**. Параметры стендовой проверки:

```json
{
  "wash_direction": -1,
  "sheath_direction": -1,
  "sample_direction": -1,
  "wash_search": 9,
  "sheath_search": 12,
  "sample_search": 10,
  "search_step": 0.5,
  "home_feedrate": 90,
  "release_distance": 12,
  "pull_off": 0.5
}
```

Это исходные стендовые значения, а не универсальная калибровка.
`search_step` определяет расстояние между чтениями M119; `home_feedrate` — скорость.
`release_distance` ограничивает отход до отпускания входа, `pull_off` добавляется
после отпускания. Увеличение `pull_off` не исправляет недостаточный поиск отпускания.
После правки параметров нажмите **Save run parameters as defaults**.

1. Убедитесь, что на общий вход не давит другой кран.
2. Нажмите **Run only this step** у `wash_valve`, затем отдельно `sheath_valve`, затем `sample_valve`.
3. Ожидайте: движение к кнопке, срабатывание, обратное движение, отпускание,
   дополнительный отвод, итог `error: null`, `endstop: false`, `motor_released: false`.
4. Повторите каждый HOME минимум трижды из разных свободных положений.
5. После каждой группы откройте **Наладка → Журнал проверок**, запишите координаты
   отхода, было ли слышно/видно нажатие, наличие люфта и повторяемость.
   Машинные результаты уже находятся в `commissioning[].data.status` активного профиля.

Если ошибка поиска/отхода механическая, приложение возвращается в idle, ось
остаётся ненайденной, её мотор отпущен. Исправьте параметр/механику перед повтором.
Ошибка USB/таймаут — другая ситуация: очередь блокируется, пока связь не восстановлена.
Не снимайте эту блокировку подменой нуля.

## 6. Два рабочих положения каждого крана

HOME задаёт начало координат у срабатывания кнопки. Рабочие соединения трубок
могут находиться далеко от этой точки и от места, где кнопка отпустилась.

1. В профиле внесите измеренный допустимый ход и `home_direction: min` для A/B/C.
   Сохраните и примените профиль. Снова выполните HOME кранов.
2. В **Наладка → Движение и подтверждённый ноль** выберите нужную ось.
3. Через поле **Перемещение со знаком** и кнопку **Переместить найденную ось с удержанием**
   доведите кран до рабочего соединения. Этот jog проверяет программные пределы
   и сохраняет ссылку на ноль; обычный Service jog в Valve bench делает её недостоверной.
4. Проверьте, какие трубки соединены: визуально по конструкции или небольшим
   потоком тестовой жидкости в открытый тракт. Не считайте поворот вала доказательством маршрута.
5. В блоке **Рабочие положения крана** выберите кран и нажмите
   **Взять текущую координату в A**. Аналогично найдите второе положение и нажмите
   **Взять текущую координату в B**.
6. В заметках распишите оба соединения и способ проверки, подтвердите оба маршрута
   и нажмите **Сохранить калибровку крана в профиль**.
7. Повторите для остальных кранов. Профиль сохраняет обе координаты,
   `calibrated: true`, заметки и запись с датой. Примените накопленные изменения,
   заново выполните HOME, проверьте переключение `set_valve` в обе стороны.

Сопоставление слотов имён процедур хранится в `valves[].position_names`:

| Кран | Слот A | Слот B |
| --- | --- | --- |
| wash_valve | КП-ПРОКАЧКА | КП-ПРОМЫВКА |
| sheath_valve | КО-ПРОКАЧКА | КО-ЗАБОР |
| sample_valve | КС-ПРОКАЧКА | КС-ЗАБОР |

Если физические назначения обратные, измените `position_names` или координаты
слотов в профиле, сохраняя согласованность. Слот B не означает отрицательную координату.
Скорость обычного переключения задаётся `axes[].feedrate_default`; отдельный
`set_valve` допускает `feedrate` и `acceleration` через JSON процедуры.

## 7. Нули и направления насосов

Для каждого X/Y проверьте направление к нулю, реальный крайний ход и пригодность
концевика. Рабочий ноль должен повторяться до перехода к дозам.

**Рабочий датчик, проверенная прошивка:** используйте HOME конкретной оси на Control,
сначала с наблюдением за механизмом. Настройка `home_direction` в профиле управляет
программными границами, а не меняет направление G28 в Marlin.

**Датчика нет, либо нужна ручная установка:** при снятом удержании установите
механизм в известное положение. На Наладке выберите ось, укажите физическую
координату, опишите способ установки и нажмите **Подтвердить физическую координату**.
Команда задаёт G92 и включает удержание без движения. Это явное утверждение
инженера, а не автоматическое обнаружение нуля.

Для непрерывно вращающегося U можно выбрать условный ноль 0 в свободном положении;
это начало счёта дозы, не механическая калибровка. Ход U остаётся конечным:
перед длинной серией проверьте, хватает ли диапазона на суммарную промывку.

Проверьте малым движением, какой знак выдавливает жидкость. Сохраните:

- `pumps[].dispense_direction`: +1 или −1;
- `axes[].home_direction`, `travel`, `feedrate_default`, `feedrate_max`, при необходимости `accel_max`;
- условия установки нуля и работоспособность входа — в журнале.

Пример согласованной системы координат: если выдавливание идёт в отрицательную
сторону, а пустой шприц имеет координату 0, заполнение увеличивает положительную
координату; используйте `home_direction: min`, диапазон `[0, travel]`, `dispense_direction: -1`.
Это пример, не готовое назначение для X/Y вашего прибора.

## 8. Измерить коэффициенты объёма X, Y и U

Для каждого насоса отдельно, на одинаковой жидкости, скорости и нагрузке:

1. Установите проверенные положения кранов, заполните тракт, уберите воздух.
2. Найдите или установите ноль. Задайте короткое известное перемещение без упора.
   Можно использовать Workbench на Control с единицами **STEP pulses** и **STEP pulses/s**,
   либо Наладку с единицами оси. В последнем случае
   `step_pulses = abs(перемещение) × steps_per_unit`.
3. Соберите жидкость и измерьте объём в мкл либо прирост массы в граммах.
   При взвешивании укажите плотность в г/мл для своей жидкости и температуры.
4. Выполните минимум три повторения. Возвращайте шприц в исходное состояние
   по проверенному маршруту; не пытайтесь бесконечно выдавливать пустой шприц.
5. На Наладке выберите насос, знак выдавливания, введите реальные строки:

```json
[
  {"step_pulses": 800, "volume_ul": 124},
  {"step_pulses": 800, "volume_ul": 126},
  {"step_pulses": 800, "volume_ul": 125}
]
```

Числа выше — только пример формата. Альтернатива: `{"step_pulses":800,"mass_g":0.125,"density_g_ml":1.0}`.
В каждой строке укажите либо объём, либо массу. `step_pulses` — число STEP-импульсов
по действующему M92, а не число полных шагов из паспорта двигателя.

6. В условиях укажите направление, скорость, ускорение, жидкость, тип шприца или
   трубки, противодавление и способ измерения. Подтвердите реальные измерения и
   нажмите **Рассчитать и сохранить измерения и коэффициент**.
7. Проверьте `volume_per_unit_ul`, число повторов и `relative_stddev` в сохранённой
   записи. Формула: среднее `(мкл / STEP)` по повторам, умноженное на `steps_per_unit`.
   Коэффициент в профиле меняется, активный коэффициент пока нет.
8. После калибровки всех насосов примените профиль и снова установите нули.
9. Выполните независимые контрольные дозы уже через `pump`: минимум малая и рабочая
   доза, при рабочем расходе. Сравните измеренный и заданный объём. Допуск выберите
   с разработчиком прибора и запишите в журнал вместе с числами, а не только «ОК».
10. Повторите проверку после изменения жидкости, шприца, трубки, M92, нагрузки или скорости.

## 9. Ограничить насосы проверенными положениями кранов

В JSON профиля у каждого `device_map.pumps[]` заполните `allowed_routes`.
Ниже пример синтаксиса для насоса пробы; реальные сочетания сначала проверьте:

```json
"allowed_routes": {
  "aspirate": {
    "wash_valve": ["КП-ПРОКАЧКА"],
    "sample_valve": ["КС-ЗАБОР"]
  },
  "dispense": {
    "wash_valve": ["КП-ПРОКАЧКА"],
    "sample_valve": ["КС-ПРОКАЧКА"]
  }
}
```

Внутри одного направления условия по всем указанным кранам должны выполняться.
Несколько имён в массиве означают допустимые альтернативы для одного крана.
Для U промывка использует `dispense` и два положения sample_valve в разные моменты.
Если требуется запрет конкретных сочетаний между несколькими кранами, простая
матрица альтернатив не выражает все такие зависимости: разделите режимы на
разные процедуры и обсудите более строгую модель маршрутов.

Сохраните и примените профиль. После повторного HOME убедитесь, что насос
разрешён на рабочем маршруте и отклоняется на неправильном **до движения**.
Проверка использует найденную программную координату крана, не измеряет поток.
Пустые `allowed_routes` сохраняют старое поведение без проверки, но проверка
готовности наладки отмечает их как незаполненные.

## 10. Проверка периода U из таблицы

Таблица просит определить число шагов между двумя срабатываниями датчика насоса
промывки. Это отдельная проверка от измерения объёма жидкости.

1. Установите, есть ли на U датчик, формирующий повторяющийся сигнал при свободном
   вращении. Найдите его канал M119 и проверьте оба уровня вручную.
   Обычный механический упор нельзя использовать как датчик оборота.
2. В **Наладка → Датчик оборота** введите проверенный канал, направление, шаг опроса,
   максимальный суммарный ход, наблюдения. Скорость берётся из поля **Скорость**
   блока движения, предел этой проверки — 120 единиц/мин.
3. Нажмите **Измерить период U и сохранить результат**. Насос продолжает вращаться
   в одном направлении, счёт идёт между первым и вторым фронтом нажатия.
4. Ожидайте `period_axis_units`, `commanded_pulses_per_period`, `sampling_step_units`.
   Результат сохраняется в журнале; после проверки U обесточен и требует нового нуля.
5. Повторите минимум трижды. Число импульсов здесь вычисляется по командам и M92,
   оно не доказывает отсутствие пропусков. Погрешность обнаружения фронта — до шага опроса.
6. Если датчика нет, не изобретайте канал. Зафиксируйте отсутствие и согласуйте,
   добавляется ли датчик или этот пункт таблицы заменяется объёмной проверкой.
   В записи `wash_period` явно укажите принятое решение и с кем согласовано.

## 11. Настроить процедуры из таблицы

Все исходные процедуры — черновики. Сначала проверяйте отдельные шаги.

| Процедура | Назначение | Что ввести / проверить |
| --- | --- | --- |
| `home_valves_shared` | Последовательный поиск A/B/C | Знаки, дистанции, скорости, отход |
| `reference_pumps` | Получение/проверка нулей насосов | По умолчанию только `require_reference` X/Y/U. Если датчики проверены, замените соответствующие проверки испытанными `home` шагами |
| `startup` | Найти краны, поставить рабочие положения, проверить нули насосов | Именованные положения, вызовы HOME, `reference_pumps` |
| `wash` | Промыть кювету, переключить C, промыть пробозаборный тракт | `cuvette_volume_ul`, `cuvette_flow_ul_min`, `sampler_volume_ul`, `sampler_flow_ul_min`, `acceleration` |
| `sample_intake` | Забрать пробу и обжимающую жидкость | Объёмы, расходы, ускорение обоих насосов, маршруты |
| `analysis_delivery` | Подать обе жидкости на измерение | Те же параметры; отношение расходов задаётся выбором расходов |
| `measurement_iteration` | Забор → подача → промывка | Параметры дочерних процедур |
| `cyclic_measurement` | Начальная промывка, затем N итераций | `cycles`, объёмы/расходы, ускорение, передача параметров в дочерние вызовы |

По умолчанию `startup` не выполняет непроверенный G28 насосов: сначала физически
установите нули X/Y/U, либо настройте `reference_pumps` под реально проверенные датчики.
Не заменяйте `require_reference` на автоматический G92 без физической установки.
Насосы к моменту старта должны находиться в согласованном исходном состоянии,
а краны — иметь свободный ход к общему концевику.

Обычное `set_valve` поддерживает в JSON `feedrate` и `acceleration`. Без них
используется скорость оси и текущее ускорение прошивки. Краны с общим входом
переключаются последовательно. В таблице указано параллельное переключение:
текущая реализация воспроизводит конечные состояния, но не эту оптимизацию времени.

В `pump_multi` насосы начинают вместе. Если расчётные времена различаются, движение
разбивается на участки: сначала оба, затем оставшийся насос. Объёмы и заданные
номинальные расходы сохраняются, но разгон/торможение и стыки Marlin влияют на время.
Точная независимая временная синхронизация этой платой пока не гарантируется.

Пример для первого испытания, **не готовый рецепт прибора**:

```json
{
  "sample_volume_ul": 20,
  "sample_flow_ul_min": 40,
  "sheath_volume_ul": 100,
  "sheath_flow_ul_min": 200,
  "acceleration": 10
}
```

Отношение расходов здесь 5:1, номинальное время обеих подач — 30 секунд.
Если задано время `t` в секундах, используйте `объём = расход × t / 60`.
Не задавайте несовместимые объём, расход и время как независимые пожелания.
После выбора рабочих параметров **Save run parameters as defaults**.

**Неоднозначности исходной таблицы, которые нужно решить на приборе:**

- Для забора таблица явно перечисляет не все три крана; черновик дополнительно
  устанавливает C в КС-ЗАБОР. Проверьте этот маршрут.
- В строках и забора, и подачи написано положение насосов MAX. В коде забор
  означает `aspirate`, подача — `dispense` с заданным объёмом. Подтвердите смысл,
  не копируйте MAX буквально в обе команды.
- Исходная таблица задаёт и время, и объём промывки. В коде выбран объём и расход;
  время вычисляется. Если важнее длительность, пересчитайте объём по формуле выше.
- Порядок startup и проверка датчиков насосов должны соответствовать свободным
  маршрутам жидкости. Испытайте это перед автоматическим стартом.

Запишите принятые решения в журнал, измените шаги в Procedures и сохраните.

## 12. От отдельных шагов к полной работе

1. Примените окончательный профиль, установите нули X/Y/U, выполните HOME A/B/C.
2. Проверьте каждый `set_valve` и каждый короткий `pump` / `pump_multi` отдельно.
   Контролируйте движение, выход жидкости и соответствие разрешённому маршруту.
3. Проверьте `wash`, затем `sample_intake`, затем `analysis_delivery` по шагам.
   Для повторного забора освободите достаточный ход шприцев; для повторной подачи
   в них должен быть необходимый объём.
4. Снимайте `Draft` у проверенной дочерней процедуры и сохраняйте её. Полный запуск
   не разрешается, если любой вложенный вызов остаётся Draft.
5. Настройте/испытайте `reference_pumps`, затем полный `startup` и одну
   `measurement_iteration`. Убедитесь, что переключения не теряют нули кранов.
6. Настройте `cyclic_measurement` сначала на один цикл, затем на два. Проверьте
   расход жидкости, остатки в шприцах, отсутствие упора, утечек и воздуха.
   U накапливает координату между промывками: учитывайте его конечный диапазон.
7. После окончательного сохранения профиля и процедур заполните все пункты
   **Журнала проверок**. Для объёмов впишите измеренные значения и допуск;
   для полного цикла — параметры, число циклов и фактические наблюдения.
8. Нажмите **Проверить готовность**. Статическая часть должна быть без `issues`,
   `active_matches: true`, `unreferenced_axes: []`, все вложенные Draft сняты.
   Незавершённые физические проверки не заменяются успешным Preview.

Журнал связывает проверки с конфигурацией оборудования и процедурами.
После изменения настроек старые проверки показываются как устаревшие; проверьте
затронутые действия и заново подтвердите применимые результаты. Старые записи
не удаляются. Поле `ready` объединяет активность профиля, нули, статические проверки,
Draft и подтверждения инженера; оно не является аппаратным измерением безопасности.

При `persistence_error` в статусе процедуры результат не удалось записать на диск:
сохраните текст ошибки/отчёт и исправьте доступ к каталогу до продолжения опытов.
Механическая ошибка HOME и потеря USB требуют разного восстановления;
при таймауте/ABORT координаты не считать достоверными.

## 13. Что передать обратно

В Наладке выберите итоговый сохранённый профиль и нажмите
**Скачать профиль, журнал и процедуры**. Передайте JSON-комплект вместе с кратким
описанием сборки, жидкостей, заменённых деталей и оставшихся замечаний.
Не передавайте только Git-код: измерения живут в локальном каталоге конфигов.

На другом компьютере:

1. Установите ту же версию кода, запустите приложение без движения.
2. В Наладке выберите JSON и нажмите **Импортировать комплект**.
   Одноимённые локальные файлы заменятся, поэтому сначала скачайте резервную копию.
3. Откройте импортированный профиль. Скорректируйте только порт подключения,
   если он отличается. При изменении transport/firmware перезапустите с
   `--profile ИМЯ`; иначе используйте **Применить сохранённый профиль**.
4. Заново найдите нули и проверьте датчики. Старые `homed` не переносятся.
5. Запускайте проверенные процедуры с сохранёнными рабочими параметрами.

Завершение наладки: после новой сессии установлены нули, проходят startup,
wash, sample_intake, analysis_delivery и циклическое измерение; все рабочие
координаты, направления, коэффициенты и параметры находятся в экспортированном
комплекте, а не в памяти наладчика или отдельной переписке.
