## Принятая модель

Один микрик крана задаёт повторяемый ноль. После Home кран освобождает микрик;
рабочие позиции выбираем визуально и сохраняем как смещения от нуля. Второй
концевик для этого не требуется. Сейчас FlowEngine сохраняет два положения A/B.
Название шага может описывать их назначение: например, «КС-ПРОКАЧКА».

Оси A/B/C в текущем профиле используют единицы Marlin, обозначенные `mm`.
Это не измеренные градусы выходного редуктора. Для ввода настоящего угла нужно
отдельно определить пересчёт. Числа из старого приложения не подтверждают его.

У X/Y по два микрика. Физическая калибровка определяет ход и направление;
Home восстанавливает текущую привязку. Это разные действия. Уже сохранённая
калибровка X/Y не заменяется числами из архива.

## Что сделано

- Один и тот же конструктор находится на главной странице и в «Сценариях».
  Ручное управление и диагностика на главной свёрнуты ниже.
- Можно добавлять, изменять, копировать, удалять и переставлять шаги.
  У процедур и шагов есть отдельные понятные названия; имя YAML остаётся латинским.
- Есть положения и Home кранов, Home осей, перемещения, подача объёма,
  совместный ход, пауза, вложенная процедура, датчики, журнал и управление удержанием.
- Для положения крана можно задать скорость и ускорение в шаге. Пустая скорость
  использует профиль. Ускорение временное: прежний M204 восстанавливается;
  EEPROM и токи драйверов не меняются. Прежние ограничения скорости сохраняются.
- «Проверить без движения» сохраняет YAML и разворачивает план через существующий
  API preview. Команды контроллеру не отправляются. Результат показывает порядок
  и недостающие настройки.
- Пункт `require_setup` хранит незавершённое требование. Он не исполняется.
  API запрещает полный запуск и запуск такого выбранного шага даже при снятом
  флаге черновика; проверяется также содержимое вложенных процедур.
- Старые YAML без новых полей продолжают загружаться. JSON и экспорт остаются
  в разделе разработчика. Сохранения идут в прежний пользовательский overlay.

Используются прежние слои: Jinja/JS → `/api/procedures` → Pydantic DSL →
composer/preflight → ProcedureRunner → GcodeSender → CommandQueue.
Отдельного serial-подключения или второго исполнителя нет.

## Черновик «Запуск» по таблице

Файл: `config/procedures/startup_draft.yaml`. Подключение, COM и baudrate берутся
из активного профиля; открывать порт из шага процедуры не нужно.

1. Home крана промывки; затем его рабочее положение КП-ПРОКАЧКА.
2. Home крана обжимающей жидкости; затем КО-ПРОКАЧКА.
3. Home крана сэмплера; затем КС-ПРОКАЧКА.
4. Параллельная подготовка насосов X/Y в НС-MIN / НО-MIN, затем отход до рабочих позиций.
5. Проверка насоса промывки U: два последовательных срабатывания датчика,
   число шагов между ними, сохранение результата.

Рабочие положения пока отмечены как требующие настройки. Нельзя заранее
считать A или B положением «Прокачка». В таблице фразу про движение при уже
нажатом микрике трактуем как опечатку: сначала освобождение, затем поиск.
При общем z_min и неизвестном источнике нажатия сохраняется штатный сервисный
отход выбранного крана; другие краны для выяснения источника не двигаются.

## Что уточнить и доделать у аппарата

1. Завершить наблюдаемый пробный Home C, затем сохранить визуальные рабочие A/B.
   Последний известный факт: C− ведёт к микрику; полный Home ещё не завершался.
2. Проверить направление и Home остальных кранов, записать назначение их A/B.
3. Уточнить таблицу разрешений: при каких положениях трёх кранов можно двигать
   каждый насос и в каком направлении. Пока автоматической проверки этой
   гидравлической конфигурации нет; наличие координат не означает её разрешение.
4. Уточнить, какой физический конец X/Y инженеры называют MIN, и рабочий отход.
   Сейчас `home` с X,Y выполняется последовательно. `move_multi` / `pump_multi`
   дают согласованный ход, а не независимый поиск. Текущий поиск использует общий
   M410: для настоящего параллельного Home нужен отдельный алгоритм остановки осей.
5. Выяснить вход датчика U и направление, затем добавить отдельную проверку
   периода с ограничением времени/пути и сохранением измерения. Сейчас её нет.
6. Подставить проверенные действия в черновик и проверить его по шагам.
   После этого можно собирать следующие процедуры в этом же конструкторе.

Успешные штатные Home/Go сохраняют удержание. Для паузы без питания обмоток есть
отдельный шаг отключения моторов; он сбрасывает привязку и требует нового Home.
Код конструктора не повышает токи и сам не запускает движения при открытии страницы.

Последнее аппаратное состояние: [COMMISSIONING_STATE.md](COMMISSIONING_STATE.md).

## Единицы и люфт — дополнение 22 октября

Инженерам нужны физические единицы. Предлагаемый интерфейс:

| Узел | Положение / объём | Скорость | Ускорение механизма |
| --- | --- | --- | --- |
| Шприцы X/Y | мм хода поршня; для дозирования мкл или мл | мм/с; мкл/мин или мл/мин | мм/с² |
| Краны A/B/C | градусы выходного вала | градусы/с | градусы/с² |
| Насос U | обороты; для дозирования мкл или мл | об/мин; мкл/мин или мл/мин | об/с² при необходимости |

Это требование к следующему этапу, а не уже реализованный физический пересчёт.
В текущем move `units=axis` означает единицы координаты профиля, `units=steps` —
импульсы STEP. `speed_units` отдельно задаёт единицы скорости. Пересчёт STEP/s
и axis/s в F уже есть; для объёма есть `volume_per_unit_ul` и калибровка по
измеренной жидкости. Компенсации люфта в текущем коде нет.

Сохраняем нынешние координаты и M92, чтобы не менять существующую привязку и
записанные положения. Физический масштаб вводим отдельным измеренным коэффициентом
`k = физическое перемещение / изменение координаты Marlin`. Тогда для одной оси:

- перемещение контроллера = требуемое физическое перемещение / k;
- F = 60 × физическая скорость в секунду / k;
- ускорение контроллера = физическое ускорение / k.

Для расхода в мкл/мин используется F = расход / `volume_per_unit_ul`.
При нескольких осях общий F рассчитывается через их согласованный ход, как в
нынешнем `move_multi` / `pump_multi`, а не копируется в каждую ось отдельно.
До измерения коэффициента нельзя просто переименовать mm в градусы или считать
найденное между микриками расстояние измеренными физическими миллиметрами.
Измеряем участок после выбора люфта; масштаб и холостой ход не смешиваем.

По сообщению инженеров при реверсе мотор сначала выбирает люфт передачи/поршня.
Для калибровки нужно наблюдать выход механизма, а не только M114/Count:
двигаться в одну сторону до уверенного движения, развернуть привод и измерить
холостой ход до начала движения выхода. Повторить в обе стороны несколько раз.
Один лишь общий сигнал микриков не измеряет такой холостой ход во всём диапазоне.

Предлагаемая реализация после измерений:

- отдельные значения люфта для переходов +→− и −→+ на каждом приводе;
- раздельный учёт координаты мотора и полезного перемещения механизма;
- учёт текущей выбранной стороны и оставшегося люфта при коротких реверсах;
- выбор люфта добавляется при необходимости и не засчитывается в полезный
  ход/объём; это приближение требуется проверить измерением реальной подачи;
- после отключения мотора, ручного перемещения или потери связи состояние
  выбранной стороны считается неизвестным; Home задаёт его только с учётом
  всех своих фактических смен направления;
- проверка крайних положений учитывает полный моторный ход, включая компенсацию;
- слой компенсации один: либо приложение, либо прошивка, чтобы не прибавлять её дважды.

У Marlin есть M425, но доступность и поддержка нужных осей зависят от сборки.
На установленной плате их пока не проверяли. Команды M425/M92 и новые аппаратные
пробы в рамках этого обсуждения не отправляются.

Документация Marlin: [движение и F](https://marlinfw.org/docs/gcode/G000-G001.html),
[steps/unit](https://marlinfw.org/docs/gcode/M092.html),
[ускорение](https://marlinfw.org/docs/gcode/M204.html),
[компенсация люфта](https://marlinfw.org/docs/gcode/M425.html).
